## Module 06 — Prefetch

**Concept:** `queryClient.prefetchQuery()` — load data before the user needs it so navigation feels instant.

### Interactive Demo

- Grid of 20 Pokémon (same layout as Module 01)
- `onMouseEnter` on each card triggers `queryClient.prefetchQuery({ queryKey: ['pokemon', name], queryFn: () => fetchPokemon(name) })`
- Inspector updates in real time — query enters cache with status `fresh` on hover
- Clicking the card opens a bottom sheet **instantly** (no spinner — data already cached)
- Cards that have been prefetched show a subtle visual indicator (small badge or border highlight)

### Key Learning Moments
- Inspector shows query becomes `fresh` *before* the user clicks
- Clicking a non-hovered card shows normal loading; clicking a hovered card is instant — side-by-side comparison is visible
- `prefetchQuery` does not double-fetch if data is already fresh

### Panels
- **EngineeringInsight06:** Problem (navigation feels slow) → Observation (data can be loaded before click) → Solution (`prefetchQuery` is silent, no UI disruption, skips fetch if already fresh)
- **VisualDiagram06:** Two flows side-by-side — *without prefetch*: click → fetch → wait → render; *with prefetch*: hover → prefetch (background) → click → instant render
- **SourceCodePanel06:** Highlight `useQueryClient()` hook + `onMouseEnter` prefetch handler
- **ModuleSummary06:** Key takeaway: prefetch = optimistic loading without optimistic UI

## Module 07 — Dependent Query

**Concept:** `enabled: !!dependency` — the second query only fires after the first resolves and provides the required value.

### Interactive Demo

- User selects a Pokémon from a small picker (6 starter Pokémon: Bulbasaur, Charmander, Squirtle, Chikorita, Cyndaquil, Totodile)
- **Query 1:** `['species', name]` → `GET /pokemon-species/{name}` → extracts `evolution_chain.url`
- **Query 2:** `['evolution', evolutionUrl]` → `GET {evolutionUrl}` → `enabled: !!evolutionUrl`
- UI shows two sequential "step cards" that illuminate one at a time:
  - Step 1: "Fetching species data…" → resolves → shows flavor text
  - Step 2: "Fetching evolution chain…" (grayed out until step 1 done) → resolves → shows evolution chain
- Inspector shows Query 2 is absent until Query 1 completes

### Key Learning Moments
- Query 2 does not appear in the Inspector at all while Query 1 is pending
- Switching to a different Pokémon resets the whole sequence visibly
- Clear demonstration: `enabled: false` = query dormant, not failed

### Panels
- **EngineeringInsight07:** Problem (data B needs an ID from data A — parallel fetch impossible) → Observation (all queries run in parallel by default) → Solution (`enabled` flag as a gate; falsy = query stays dormant, not errored)
- **VisualDiagram07:** Timeline — Query 1 running | Query 2 (pending, dimmed) → Query 1 done → Query 2 starts → both done
- **SourceCodePanel07:** Highlight `const evolutionUrl = species?.evolution_chain.url` + `useQuery({ ..., enabled: !!evolutionUrl })`
- **ModuleSummary07:** Key takeaway: `enabled` converts any value into a query gate; falsy = dormant

### New API calls needed

### New types needed

## Module 08 — Mutations

**Concept:** `useMutation` — write to "server", handle loading/error/success lifecycle, sync UI via `invalidateQueries`.

### Interactive Demo — "My Pokémon Team"

**Fake server:** `useRef<string[]>` holding current team names (initial: `['bulbasaur', 'charmander', 'squirtle']`). This ref lives at module level, persists across re-renders, simulates a real backend.

**Layout:**
- Top: browse grid of 20 Pokémon with "Add to Team" button on each card
- Bottom: "My Team" panel — current team members as cards, each with a "Remove" button
- "Simulate Error" toggle switch — when on, next mutation fails after delay

**Add mutation:**
- `useMutation({ mutationFn: async (name) => { await delay(800); fakeServer.add(name) }, onSuccess: () => queryClient.invalidateQueries({ queryKey: ['team'] }) })`
- Button shows spinner + disabled during `isPending`
- On success: team panel refreshes automatically

**Remove mutation:**
- Same pattern, 600ms delay
- Button shows spinner + disabled during removal

**Error demo:**
- With "Simulate Error" on: mutation throws after delay
- Button turns red, error message appears below team panel
- Team does not change (server rejected)

**Team query:**
- `useQuery({ queryKey: ['team'], queryFn: () => Promise.resolve([...fakeServer.current]) })`

### Panels
- **EngineeringInsight08:** Problem (`useQuery` is read-only — need a way to write to server) → Observation (mutations have a different lifecycle: fire-once, not auto-retry, no background refetch) → Solution (`useMutation` + `onSuccess: invalidateQueries` as the bridge between write and read)
- **VisualDiagram08:** Flow: click button → `mutate()` → `isPending: true` → server response → `onSuccess` → `invalidateQueries` → query refetch → UI update
- **SourceCodePanel08:** Highlight `useMutation({ mutationFn, onSuccess })` + `mutation.mutate(name)` + `mutation.isPending`
- **ModuleSummary08:** Key takeaway: mutations and queries live separately; `invalidateQueries` is the bridge

## Module 09 — Advanced Cache

**Concept:** `setQueryData` vs `invalidateQueries` — two ways to update cache after a mutation, with different trade-offs.

### Interactive Demo — "Cache Surgery"

Same "My Pokémon Team" scenario as Module 08, but now the user controls the cache update strategy.

**Cache Strategy toggle (prominent in UI):**
- `setQueryData` — update cache directly with known result, no network call
- `invalidateQueries` — mark cache stale, trigger refetch from "server"

**Behavior in each mode:**

*setQueryData mode:*
- After mutation completes, call `queryClient.setQueryData(['team'], newTeamArray)` directly
- UI updates instantly
- Inspector: query never enters `fetching` state — data is replaced in-place
- Status strip: "Updated via setQueryData — no refetch"

*invalidateQueries mode:*
- After mutation completes, call `queryClient.invalidateQueries({ queryKey: ['team'] })`
- Brief loading state as query refetches
- Inspector: query goes `stale` → `fetching` → `fresh`
- Status strip: "Updated via invalidation + refetch"

**The key visual:** user can switch strategy mid-session and immediately see the difference in how the Inspector behaves and whether there's a loading flash.

### Panels
- **EngineeringInsight09:** Problem (`invalidateQueries` always refetches — wasteful if you already know the new data) → Observation (after a mutation, the client often has the exact new state) → Solution (`setQueryData` for known-data sync, `invalidateQueries` for server-of-truth consistency)
- **VisualDiagram09:** Two parallel flows — `setQueryData`: mutation → direct cache write → done (no network); `invalidateQueries`: mutation → stale → refetch → fresh
- **SourceCodePanel09:** Show both strategies with the conditional toggle
- **ModuleSummary09:** Key takeaway: `setQueryData` = trust yourself (you know the new state); `invalidateQueries` = trust the server (re-verify)
